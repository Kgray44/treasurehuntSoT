# Executable desktop launcher

This is a development candidate, not the installed private v0.3.1. Its `launch_codex_task` owns app-server creation, assignment, naming, Goal, turn start and durable recovery components. Normal launches stop before creation: live tests showed that desktop membership required the host's `set_thread_title` operation before assignment was recognized. App-server naming/assignment alone left native membership null. `action:status` plus `request_key` reads a receipt without dispatching. Installation and ordinary-Chat invocation remain unverified.

Local MCP uses Python 3 and the owner's installed Codex runtime. It reuses Codex's existing authorized account/configuration without reading or copying credentials. Setup requires an owner-local `CODEX_HOME/launchdeck-state/native-binding.json` (default `~/.codex/launchdeck-state/`) containing `codexBinary`, `workspaceRoot`, `desktopProjectId`, and `appServerProjectId`. Normal launch additionally requires both `desktopAssociationVerified:true` and `pluginOnlyAssociationVerified:true`; the latter is currently false. Never set it from a host-assisted test. On 2026-10-10, assignment to app-server VoyageWright `01a11764-14e9-7de3-9f5d-913e839c7c37` was observed in existing desktop project `fd21b701-3215-417a-a413-0a17e02badbb` only after host title registration. Merely setting cwd, using app-server naming, or assigning its project was insufficient. Binding files and journals stay outside the distributable plugin.

The tool uses public `thread/start`, experimental `thread/metadata/update`, `thread/name/set`, `thread/goal/set/get`, `turn/start`, `thread/read/resume/list`. Experimental API is explicitly negotiated. It never calls private app IPC, migrates the source Chat, creates projects or relays, copies cookies, or launches an Agents API session. Native app-server project identity and desktop project identity remain separate in the returned evidence.

`requested_project_id`, if supplied, must match the verified desktop binding. The existing planner supplies Project Trim contracts and names. Inventory includes active and archived threads from all supported sources plus journal reservations; preexisting desktop-only membership not represented in app-server cannot be claimed globally complete. Human edits or independent launchers can still race title assignment. Same frozen request reuses its fingerprint and observed ID; a fresh run requires the existing explicit `new_run` authorization fields. A failed reservation with no returned identity stops for reconciliation rather than creating again. A partial launch with a stored ID repairs that chat. A stored turn ID is never started twice.

For an authorized independent worktree, pass `environment:worktree` and `worktree_authorized:true`. The adapter fetches main and creates an owned Git branch/worktree under the state directory; it records actual SHA/path, preserves existing worktrees and does not merge, tag, release or delete worktrees. Local launches use the bound workspace.

Native Goal objective contains the request marker and accepted objective (maximum 3800 characters; detailed scope remains in the turn prompt). Budgets require the existing explicit human-budget fields. The target must complete its native Goal only when all acceptance criteria are satisfied. Active Goals can automatically continue; a final reply alone is not Goal completion. An explicitly disposable test may pass `read_only:true`, `environment:local`, and `disposable_marker:<exact expected reply>`. Its Goal is paused during one explicit turn, then completed only after the exact marker is observed.

The local MCP server owns its app-server child. Closing/reloading that server stops its owned runtime; transcripts, project assignment, Goals and receipts remain durable. After reconnection, a stored turn is not assumed still running. The result exposes accepted turn ID separately from live status and names unavailable approval forwarding. Native interactive/approval requests are rejected with a truthful limitation; no approval is fabricated. Open the real target chat for supported owner interaction when necessary. `link:null` means no verified link was returned by the protocol; do not invent one.

Ordinary Chat -> executable tool -> native desktop project acceptance remains a separate live gate. Do not report it passed merely because packaging, installation, MCP transport tests or native component launches passed. Keep PR #696 draft and unmerged until the owner-required full gate passes.
