# Reach startup capacity and geometry integration

This candidate continues [PR #769](https://github.com/Kgray44/treasurehuntSoT/pull/769) from `cd34451832e2d0004492880ac1288ec31945d3b2`. It integrates the previously private startup capacity screen with the actual camera dimensions and repairs retained hand pixels after Stop. It is a bounded startup/performance correction, **not acceptance of the full perception mission or Phase 1 physical reliability**. Application validation remains failed; no protected integration or owner-preview deployment is claimed.

## Problem and resulting behavior

The [preceding experiment](Phase_1_Startup_And_Cap_Experiments_20261019.md) reproduced a GPU worker that initialized successfully yet returned 82/82 results beyond the unchanged 150 ms limit. The same pinned region provider on CPU completed its photographic journey with 60/60 timely results. A private fixed-size startup screen then selected CPU automatically and returned 55/55 timely results. Those are separate controlled Chromium journeys, not a physical camera trial or synchronized paired pixels. CPU/GPU localization can differ materially; the existing identity and coordinate gates remain necessary.

The source candidate snapshots delivered video dimensions after playback starts. Optional INIT, synthetic probes, READY and live bitmaps must agree with that geometry, lease generation and mirror transform. A resize while the worker starts or while bitmap extraction awaits invalidates the source before a frame reaches inference. The canonical Sextant 1–16384 dimension contract validates metadata; it does not promise device/allocation support at every permitted size.

The worker performs its existing small warmup at timestamp -3, followed by two gray probes at -2 and -1, each at the delivered dimensions with global palm inference and two distinct forced landmark regions. Both probe costs must be finite, nonnegative and at most 150 ms. The first native-size allocation, compilation and readback cost is included. Synthetic results and retained regions are discarded, never passed to identity, readiness or calibration consumers.

If GPU fails capacity screening, its graph must close successfully before one CPU region-provider attempt. READY identifies the actual backend and provider policy. Generic initialization failure retains the original CPU fallback. If CPU region-provider screening also fails, its pre-READY error can invoke that unchanged parent fallback to the unscreened original CPU graph within the same total budget. The one-attempt bound applies to worker-internal CPU region retries, not every application graph. The parent requires complete successful region-provider evidence matching its source geometry. Only the known original-worker fallback permits older omitted policy metadata; the optional worker's internal original-CPU fallback identifies itself explicitly. Unknown startup messages cannot silently initiate that fallback.

The 12-second optional and 15-second total startup deadlines remain unchanged. A screen is only a necessary capacity condition before live observations; every live result still passes the existing current-image, pixel-origin and 150 ms checks. There is no silent backend switch after READY. Camera/bitmap geometry errors stop the session and invalidate setup. Calibration architecture, coordinate bounds, selected-index source proof, fifteen samples/600 ms holds and the five-target independent raw 3% check are unchanged.
