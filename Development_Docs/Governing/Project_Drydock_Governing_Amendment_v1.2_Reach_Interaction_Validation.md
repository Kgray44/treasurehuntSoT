# Project Drydock v1.2 — Reach Interaction Validation

## 1. Additive authority

Drydock already has [v1.1 spatial/provider integration](Project_Drydock_Governing_Amendment_v1.1_Spatial_Provider_and_Device_Lab_Integration.md). This is v1.2 to preserve that accepted version. The v1.0 Chronicle verification/simulation baseline and v1.1 spatial requirements remain effective. Reach adds an interaction-validation domain; it does not create a second canonical runtime.

## 2. Definition validation

Validate interaction-definition version, semantic target reference/version, target kind, permitted operations, constraints/units/frames, visibility/access scope, owner outcome, confirmation and cancellation policy, fallback route and declared evidence requirements. Unknown operations, nonfinite transforms, inverted scale bounds, unsupported target-operation combinations and missing essential alternatives are errors.

A camera capability does not prove calibrated pointing. Optional hover polish may degrade; an essential mechanic must have an equivalent usable path. Native-only monitoring cannot be silently required by a browser-baseline interaction. Private calibration and raw footage must never be packaged as Chronicle content.

## 3. Authority and progression analysis

Reach events are non-progression intent. A valid completion path must reference the applicable owner-domain result and canonical runtime completion rule. Reject a mechanic that advances because an uncertain hover, missing hand or raw release classification was observed.

Crossdeck-backed mechanics require appropriate transaction acceptance/acknowledgment. Parallax mechanics require accepted constrained spatial results. Conventional alternatives may produce the same narrative result through their own truthful evidence class. Reach is not identity verification or anti-cheat.

## 4. Deterministic simulation

Simulate observation availability, confidence/freshness, target ambiguity, calibration state, supported operations, cancellation, stale session, target removal, owner rejection and capability fallback. Model progression through the same canonical runtime semantics used in real play. Simulator success demonstrates reachable and safe logic, not webcam accuracy.

Branch scenarios cover no camera permission, unsupported backend, provider failure, background suspension, lost hand, track swap, target-version conflict, multiple modalities, receiver rejection and missing acknowledgment. Timeouts cancel/expire rather than generate release. Replayed intents cannot satisfy current progression.

## 5. Publication evidence

Chronicle publication distinguishes content validity, supported modality, registered software proof and physical qualification. Referenced Reach capabilities carry implementation and evidence status. An unavailable optional gesture with a valid fallback may be a warning; an essential unsupported mechanic without an equivalent path blocks publication.

Drydock may require evidence classes for a particular physical claim but does not execute Sounding Line's release decision or relabel Device Lab receipts. D0/D1 cannot satisfy D4/D5 pointing requirements. An unpublished future interaction definition is not executable merely because the registry declares it.

## 6. Compatibility and implementation entry

Published editions retain operation semantics and version bindings. Changes in target selection, gesture grammar or completion-relevant constraints require versioning and compatibility review. Calibration is user runtime state and excluded from immutable packages.

Future Drydock implementation adds the typed schemas, validators, deterministic provider adapter and publication gates with focused regression evidence. This amendment alone changes none of those runtime behaviors. The current accepted Drydock implementation and its historical evidence remain intact.

## Publication and implementation boundary

This amendment is additive. Preserve the accepted baseline and all historical evidence. Its requirements become the effective documentation contract on protected-main acceptance; they do not claim new runtime implementation or passing physical qualification. Future work uses focused validation, the ordinary Sounding Line final check, protected-main integration, and a landed-tree smoke check. Sounding Line remains the software verification authority; One Voyage remains the progression authority.

The [Reach governing document](Project_Reach_Spatial_Interaction_and_Intent_System_Governing_Document_v1.0.md) defines the shared interaction contracts. The [effective spatial authority index](Voyagewright_Spatial_Experience_Effective_Authority.md) identifies the complete governing chain. Product implementation status remains explicit in the registries and project homes.
