# Preparation failure retention

The original DEVELOPMENT_ONLY [run 39881765636/1](https://github.com/Kgray44/treasurehuntSoT/actions/runs/39881765636)
used controller `1c516d27fca521157732fca4cbba773d1542f1b2`. Preparation failed;
browser execution and its execution-gated encrypted uploader were skipped.
The provider listed zero artifacts. The private setup/build streams and private
preparation result therefore had no publication route. This establishes a
retention coverage defect. The underlying preparation failure remains UNKNOWN;
this correction cannot recover the former runner's unpublished files.

The separate PREPARE route binds controller, candidate, selector digest, provider
run/attempt and a fresh host session. Source fingerprint unavailability remains
explicit. Each setup/build attempt records its true ordinal, producer class,
exit and creation-bound cleanup receipt. Prisma generation, database bootstrap,
seed, preparers and production build never acquire browser/server labels.

Capture retains at most eight producers, 16 MiB per stream, 32 MiB across all
streams and a 1 MiB private receipt. Error fields are separately bounded and
truncation is explicit. Capture continues draining after a limit is reached.
Successful zero-exit children can precede a host fingerprint, freeze, database
snapshot or manifest failure; those failures do not require an invented child
exit. If any started producer lacks verified tree and stream closure, only the
encrypted private receipt is eligible and collection is INCOMPLETE.

Only a live preparation evidence token can reach the publisher. The production
route fixes the accepted wrapping-key identity; a generated-key pure encryption
seam cannot mint upload paths. Publication stages an encrypted envelope and
allowlisted retention metadata in owned directories, validates durable exact
bytes and uses a separate preparation output nonce. The always-on-failure
uploader accepts only the preparation step's genuine exact pair. Product
children receive neither output authority nor either publication nonce.

Preparation result, collection completeness, encryption, persistence, output
selection, artifact upload and final acceptance are separate facts. Retention
failure preserves the original preparation failure. Public output contains only
redacted outcomes; private error messages, stacks and producer bytes stay inside
encryption. No raw-log fallback is permitted.

## Verification boundary

Focused verification uses inert failed setup/build children, generated test keys
and disposable files. Linux owner-ID, file ownership and filesystem fault cases
require hosted Linux proof; Windows results cannot satisfy those obligations.
Independent exact-source review, the normal protected Mainline Decision and
landed-source verification remain required before installation is claimed.

The browser retention route, protected consumer contracts, #721 finite authority,
original failed receipts and product acceptance remain unchanged. A downstream
consumer retry requires its owner's separate source-bound decision.
